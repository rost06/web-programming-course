## Зачем разделять переходы и сохранение

У попытки есть правила: нельзя редактировать завершённую работу, ответ заменяется по `taskId`, индекс не выходит за границы. Если эти правила разбросаны по обработчикам, их трудно проверить. `useReducer` собирает переходы в одну функцию. Запись в `localStorage` — отдельная синхронизация с внешней системой браузера, поэтому её выполняет `useEffect`.

## Reducer

```tsx
type State = { value: string; saved: boolean };
type Action = { type: "changed"; value: string } | { type: "marked-saved" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "changed":
      return { value: action.value, saved: false };
    case "marked-saved":
      return { ...state, saved: true };
    default:
      return state;
  }
}
```

Reducer синхронен и предсказуем: одинаковые `state` и `action` дают одинаковый результат. Не вызывайте внутри него `localStorage`, `fetch`, `Date.now()` или `Math.random()`.

## Иммутабельность и события

Событие описывает намерение, а не указание «поменяй кнопку». Например, `{ type: "answerChanged", answer: next }` понятнее, чем набор флагов. Для массива ответов создайте новый массив, удалив прежний ответ с тем же id. В `submitted` возвращайте прежнее состояние на событие изменения.

## Что такое эффект

Эффект — код, который синхронизирует React с системой за пределами React: хранилищем, таймером, подпиской или документом. Он запускается после отображения и повторяется, когда меняются зависимости.

```tsx
useEffect(() => {
  try {
    localStorage.setItem(key, JSON.stringify(draft));
  } catch {
    setStorageWarning("Черновик не сохранён; ввод продолжается в этой вкладке.");
  }
}, [key, draft]);
```

Обновление состояния от действия пользователя должно быть в обработчике или reducer, а не в эффекте без необходимости. Не пишите на каждый рендер при неполном списке зависимостей.

## Чтение и проверка JSON

`localStorage.getItem` возвращает строку или `null`, а `JSON.parse` может бросить исключение. Объявите результат parse как `unknown` (сам `JSON.parse` возвращает `any`): проверяйте объект, версию, `setId`, `status`, массив ответов и допустимые поля ответа. Случайное `as Draft` не является валидацией.

В небольшом примере настройки можно проверить вход полностью:

```ts
function readTheme(raw: string | null): "light" | "dark" | null {
  if (raw === null) return null;
  try {
    const value: unknown = JSON.parse(raw);
    return value === "light" || value === "dark" ? value : null;
  } catch { return null; }
}
```

У черновика больше полей, и нужно различать отсутствие, несовместимость и ошибку чтения. Проверка одной версии без проверки содержимого массива не подтверждает весь формат.

В задании проверяйте весь используемый формат: неизвестный ответ не должен проникать в состояние. Не путайте «нет черновика» с «черновик найден, но несовместим»: интерфейс должен объяснить второй случай и дать кнопку сброса.

## Ключ и набор

Ключ должен отличать текущий набор. Если пользователь открыл другой `setId`, старый черновик нельзя показать ему как новый. Сохраняйте id задания в каждом ответе, а не его индекс: порядок заданий может измениться.

## Ошибки хранилища

Режим приватности, квота или политика браузера могут сделать чтение и запись исключением. Ошибку перехватите, покажите предупреждение и продолжите reducer-переходы в памяти. Это деградация сохранения, а не причина запретить ввод.

## Проверка

Откройте набор, ответьте, обновите страницу. Затем в DevTools Application измените значение на `{` и обновите: должна появиться диагностика, а не белый экран. Подставьте другой `setId`, нажмите сброс и убедитесь, что новая попытка чистая. Завершите попытку, обновите страницу и проверьте, что она не стала редактируемой.
