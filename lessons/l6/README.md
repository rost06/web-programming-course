# L6. Vitest и React Testing Library

## Зачем эта тема

Код может выглядеть правильно в одном ручном сценарии и всё же терять ответ при навигации или ошибке сети. Тест фиксирует наблюдаемое правило, чтобы его можно было повторить после изменения. Vitest запускает тесты, а React Testing Library помогает проверять интерфейс так, как его видит пользователь.

Термины:

- **тест** — воспроизводимый сценарий с ожидаемым результатом;
- **unit-тест** — проверка небольшой функции или правила без DOM;
- **RTL** — запросы к доступному интерфейсу и действия пользователя;
- **mock** — контролируемая замена внешней границы, например API;
- **cleanup** — удаление DOM после теста.

До L6 `npm test` не является обязательной командой и не означает, что Vitest или тестовые зависимости уже установлены. На этом этапе подключите их к той же рабочей версии `trainer`, которая прошла L2–L5. Полный setup с точными версиями, scripts и `globals: false` описан в [гайде](docs/GUIDE.md).

## Подключение к тому же проекту

Из существующей `trainer/`, одинаково в Linux и Windows PowerShell:

```sh
npm install vitest@3.2.7 jsdom@26.1.0 @testing-library/dom@10.4.1 @testing-library/jest-dom@6.6.3 @testing-library/react@16.3.3 @testing-library/user-event@14.6.7 --save-dev --save-exact
npm pkg set "scripts.test=vitest run"
```

После установки создайте настройку окружения и setup-файл по гайду. При `globals: false` тесты импортируют `describe`, `it` и `expect` из `vitest`, а setup-файл явно вызывает `afterEach(cleanup)`. Это изолирует DOM одного теста от другого.

## Задание A6

Продолжите серверный сценарий A5 и добавьте осмысленные тесты поведения. Экран и тестовые сценарии спроектируйте самостоятельно по требованиям ниже; примеры показывают границы проверки на другой предметной области.

Покройте как минимум:

- правило заполненности и переходы между состояниями;
- сохранение ответа при навигации назад и вперёд;
- отображение ошибки отправки без потери введённого значения и доступный повтор;
- независимость от локального API и внешнего интернета.

Тест должен описывать действие пользователя или устойчивое доменное правило, а не случайный CSS, внутреннее имя state, порядок данных или snapshot всей страницы. Для сетевого сценария подмените функцию API или `fetch` на границе запроса. Подготовьте собственные экран и тесты по этим наблюдаемым сценариям.

## Проверка и запуск

Из `trainer/`, одинаково в Linux и Windows PowerShell:

```sh
npm run check
npm test
npm run build
```

Для ручного API-сценария из корня репозитория запустите учебный сервер; команда одинакова в Linux и Windows PowerShell:

```sh
node course/server/server.mjs
```

`npm test` запускает одноразовый прогон Vitest, а `npm run build` проверяет сборку. Сначала настройте scripts и зависимости на своей версии проекта, затем запускайте эти команды.

## Критерии зачёта

- тесты проверяют заполненность и переходы;
- ответ возвращается после навигации по тому же `taskId`;
- ошибка отправки видна, ввод сохранён, повтор возможен;
- DOM очищается между тестами при `globals: false`;
- сетевые зависимости контролируются, внешний интернет не нужен;
- README проекта описывает запуск и один дефект: факт, гипотезу, проверку и исправление;
- клиент не вычисляет серверную оценку; тесты показывают наблюдаемое поведение приложения.

P6 проверяет A5 и реальные запросы к API; A6 сдаётся на P7. Укажите SHA своей работы в PR. Процент покрытия — диагностический сигнал, а не главный критерий: на P7 покажите один тест, объясните, какой дефект он обнаруживает и что остаётся за его границей.
