# Как разбирать поведение приложения

[Задание](../README.md) · [Справка](CHEATSHEET.md) · [Интерактив](interactive.html)

## Факт и объяснение

Факт — наблюдаемый результат: после нажатия кнопки счётчик остался равным 2. Объяснение — предположение о причине: возможно, событие не обработалось. Одно не заменяет другое. Для проверки предположения нужны новые наблюдения: был ли вызван обработчик, изменилось ли состояние, какие данные отрисованы.

Не следует начинать с изменения нескольких частей сразу. После этого трудно понять, какое изменение повлияло на результат. Сначала сохраните точный сценарий, затем проверяйте одну гипотезу за раз.

## Пример: список покупок

Пользователь редактирует название товара, отправляет изменение и видит прежнее название после обновления страницы. Возможные причины различны: запрос не ушёл; сервер отклонил данные; ответ сервера не соответствует ожиданию; экран использовал старую копию данных.

Наличие нового текста в поле ввода подтверждает только локальный ввод. Ответ 200 и повторное чтение записи подтверждают больше, но всё ещё нужно проверить, что это та же запись. Поэтому фиксируются идентификатор записи, тело запроса и полученный результат. Номер строки в списке недостаточен, если список сортируется.

## Состояние интерфейса и внешние данные

У каждого значения должна быть понятная роль. Ввод в поле можно считать локальным черновиком. Успешно сохранённая запись известна серверу. Число заполненных полей можно вычислить из текущих данных. Если независимо хранить число и сами поля, они могут разойтись.

React рекомендует вычислять производные данные непосредственно при отображении, когда для них не нужна синхронизация с внешней системой. [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect).

## HTTP-ответ не равен успешному действию

Полученный Response ещё нужно проверить. Fetch может вернуть Response со статусом 400 или 500; это не то же самое, что отсутствие сетевого соединения. Затем нужно прочитать тело и убедиться, что его форма соответствует ожидаемой. [Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch).

Успешное сохранение и вычисленная оценка — разные события. В [контракте](../../../course/CONTRACT.md) результат текстового ответа может ожидать проверки. Значение null в поле score нельзя интерпретировать как полученный ноль.

## Регрессионная проверка

Тест должен проверять договорённость о поведении. Например, если сортировка каталога меняет порядок строк, выбранная запись всё равно должна определяться по её id. Проверка только длины списка такой дефект не обнаруживает.

После исправления повторите исходный сценарий. Затем проверьте соседний сценарий: повтор действия, пустые данные или возвращение к предыдущему экрану. Не нужно перечислять все мыслимые проверки; выбирайте те, на которые могло повлиять изменение.

## Короткий разбор

В разборе нужны: условия воспроизведения, ожидаемый результат, наблюдение, подтверждённая причина, изменение и способ проверки. Фраза «исправлены ошибки» не позволяет повторить проверку. Ссылка на конкретный коммит связывает разбор с исследованной версией.

Разбор может закончиться выводом «ошибка не воспроизведена при перечисленных условиях». Это точнее, чем утверждать полную исправность без оснований. Тогда перечислите только действительно проверенные условия.
